## 5. Werdykt techniczny

nRF54L15 bare-metal RCP traci zdolność TX pod wysokim rate dużych pakietów ICMP. Host raportuje `radio tx timeout` → RCP failure detected → recovery (1/2, 2/2) → `RecoverFromRcpFailure()` Failure. Zachowanie potwierdzone auto, ręcznie i cliff_debug. Smoke z MED/16 B przechodzi; rate 2 s + 1000 B — stabilnie (53/53 OK).

**To NIE jest:**

- brak vendor hooks (te są oczekiwanym szumem w teardown),
- problem samego setupu test framework (topologia + krótki ping często OK),
- brak hex / zły FEM (skyworks hex jest poprawny).

**To JEST:**

- bug/stabilność RCP 54L15 pod sustained TX dużych pakietów ICMP **przy wysokim rate** (0.1 s),
- ewentualnie mismatch wersji host 1270 vs RCP 1275.

**Rate vs size (cliff_debug 2026-08-06):**

| Rate | Size | Wynik |
|------|------|-------|
| 0.1 s | 1000 B | ERROR po ~48 s (ping #52), 200/210 OK przed crashem |
| 0.1 s | 512 B | ERROR po ~32 s (ping #5), 75/100 OK |
| 2 s | 1000 B | PASS 53/53 OK |

**Powiązanie z `test_alternate_rloc16`:** oba case'y wykazują 100% loss pinga w specyficznych oknach (awans roli vs sustained TX) — możliwy wspólny root cause w warstwie radio/TX RCP.

**Powiązanie z IPv6 fragmentation:** ping 1700 B→router fail, ale 1700 B→SED OK; iperf UDP 1600 B → crash RCP — wskazuje na problem TX pod dużymi/sustained pakietami, nie na brak obsługi fragmentacji jako takiej.
